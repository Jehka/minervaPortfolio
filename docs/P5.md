
# MINERVA P5 — Fault Injection and Physical Design

P5 took the hardware-verified P4 SoC in two directions: a fault-injection
campaign measuring how single-bit upsets propagate through a running CPU, and a
Sky130 hardening run taking the same RTL to GDS.

Both are finished. The campaign found two bugs in the design and the harness;
the hardening run found a third in the RTL and a fourth in a tool interaction.

---

## 1. Fault-injection campaign

### What was measured

An exhaustive single-bit sweep over a running program: every bit of every
instruction word in the workload, and every bit of its input data. 1,312 runs in
total, each one a full load / release / inject / execute / compare cycle driven
from the Zynq PS.

The workload is a 43-instruction kernel: copy 8 words while building an
order-sensitive checksum, bubble-sort them, store a signature and a done marker,
then force the dirty cache lines back to memory.

Each run is classified from what reaches data memory:

| Class     | Meaning                                                                   |
| --------- | ------------------------------------------------------------------------- |
| MASKED    | finished, all ten result words match golden                               |
| SDC       | finished (marker present), results differ — silent data corruption       |
| NO_RESULT | no marker before timeout: hung, ran away, or results never left the cache |
| INJFAIL   | the injection itself failed — a harness fault, not a result              |

### Results

| Class     | Instruction memory (1,056) | Data memory (256) |
| --------- | -------------------------- | ----------------- |
| SDC       | 517 (49.0%)                | 256 (100%)        |
| NO_RESULT | 315 (29.8%)                | 0                 |
| MASKED    | 224 (21.2%)                | 0                 |
| INJFAIL   | 0                          | 0                 |

Vulnerability by bit position follows the RISC-V encoding exactly:

- **Bits 0–6 (opcode)** are the most destructive. Bit 2 alone produces 19
  no-results out of 33, since it turns branches into JALRs and loads into other
  formats.
- **Bit 31** is the single worst bit, 27/33 no-result. It is the sign bit of
  every immediate, so small offsets become large negative ones and accesses
  leave the address map, where the crossbar never responds.
- **Bit 14 (funct3)** is the most benign, 21/33 masked.
- **Bits 7–11 (rd)** sit in the middle: writing the right value to the wrong
  register is often overwritten before it matters.

Faults in the final spin instruction are 32/32 masked — after the last
architectural store, nothing can change the outcome.

### Verification: an independent reference model

`sw/p5/model.py` is an RV32I interpreter plus a model of this SoC's memory
system: the 4 KB direct-mapped write-back cache, uncached instruction fetch, and
the crossbar address map. It predicts a class for each of the 1,312 injections
without touching hardware.

**Hardware and model agree on 1,256 of 1,256 classified injections.** The
remaining 56 are the model's UNCERTAIN class — a known opcode with an undefined
funct3/funct7, where the decoder's behaviour was not modelled.

Reaching that number took four rounds of disagreement, and every one was
informative:

| Disagreements | Cause                                                                               | Who was wrong     |
| ------------- | ----------------------------------------------------------------------------------- | ----------------- |
| 25            | Model called a run hung without checking whether results had already reached memory | Model             |
| 4             | Model required`funct3 == 0` for JALR; `id_stage.sv` decodes on opcode alone     | Model             |
| 2             | Model's step limit cut off runs that were slow but correct                          | Model             |
| 4             | Loads redirected into uncleared memory read a previous run's leftovers              | **Harness** |

### Design behaviours the campaign characterised

- **Unknown opcodes execute as NOPs.** The `id_stage` default leaves every
  control signal at zero. There is no illegal-instruction trap, so no "detected"
  class exists at all — a real gap for a fault-tolerant design.
- **An unmapped address hangs the master.** The crossbar's decoder returns -1 and
  no DECERR response is ever generated. Recovered only by the per-run reset.
- **Word loads ignore `addr[1:0]`** rather than trapping a misaligned access.
- **Idempotent faults exist.** Flipping bit 29 of the outer sort counter turns 7
  passes into 519. The run takes 1.4 ms instead of 27 µs and produces exactly
  the right answer. The same bit in the inner counter walks off the array and
  corrupts everything.

### Two bugs this found

**1. Reset-domain split (hardware).** The CPU-side AXI BRAM controllers were on
the PS peripheral reset while the CPU, crossbar and FI master were on the GPIO
reset. Asserting the CPU hold mid-fetch reset one side of a live AXI transaction;
the controller held RVALID waiting for a RREADY the freshly-reset crossbar would
never assert, and the pair deadlocked. Roughly 1 run in 6 — invisible in P4,
which reset the CPU once, and fatal to a campaign that resets it 1,312 times.

Fixed by exporting a registered `fabric_aresetn` from `p4_top` and moving both
`_cpu` controllers into the CPU's reset domain. Vivado rates this connection a
CRITICAL WARNING and recommends the original wiring; in this design the tool's
default advice is wrong.

**2. Harness state leak (software).** Only the ten output words were cleared
between runs. A faulted run storing to a stray address left data behind, and a
later run whose load was redirected there read valid-looking values and
classified as MASKED. Four rows were affected, and the classification was
order-dependent. Fixed by clearing all 16 KB each run.

A diagnostic worth recording: **never read the FI registers while the CPU hold is
asserted.** The FI master's slave port is in that reset domain; it accepts the
read and never returns RVALID, which stalls the ARM core on M_AXI_GP0 with no
timeout. The debugger then cannot halt or reset the CPU, and only a power cycle
recovers.

## 2. Physical design — RTL to GDS on Sky130

### Result

|                       |                                                                                              |
| --------------------- | -------------------------------------------------------------------------------------------- |
| Clock                 | **33 MHz (30 ns), timing-clean across all nine PVT corners**                           |
| Setup WNS             | +2.50 ns (worst corner,`ss_100C_1v60`)                                                     |
| Hold WNS              | +0.084 ns                                                                                    |
| Die area              | 1.47 mm²                                                                                    |
| Standard cells        | 128,124 (11,362 flops)                                                                       |
| Power                 | 33.7 mW                                                                                      |
| DRC                   | 0 (Magic and KLayout)                                                                        |
| LVS                   | 0                                                                                            |
| Antenna               | 0                                                                                            |
| Gate-level functional | **PASS** — post-route netlist executes the campaign workload, all ten words bit-exact |

Flow: sv2v → LibreLane (Yosys, OpenROAD, Magic, KLayout, OpenSTA) → Sky130 HD.

### Scope

The hardening boundary is the CPU, its L1 cache, the DMA engine, the AXI4-Lite
crossbar and the fault-injection master. Everything Xilinx-specific stays on the
FPGA side. Memories are flop arrays (512 B data, 256 B instruction) sized so the
design routes in reasonable time; SRAM macro integration is the next step.

A `cpu_hold` pin replaces the ZedBoard's reset GPIO, and an external host becomes
a fourth crossbar master, so a tester can load memory and read results through
one AXI4-Lite port.

### What the FPGA hid

**A 32-bit magnitude compare.** `if (remain_q <= 32'd4)` in the DMA engine. Vivado
maps it into carry logic for almost nothing; Yosys expands it into a ripple chain
of or2/or3 cells, ~15 levels and ~16 ns at the slow corner. Every one of the six
initially failing setup paths started at a `remain_q` bit and ran through it.

Replaced with an explicit reduction:

```systemverilog
wire remain_gt4 = (|remain_q[31:3]) | (remain_q[2] & (|remain_q[1:0]));
```

Equivalence was proved rather than assumed: exhaustively for all small values,
powers of two and 200,000 random inputs, then as a sequential SAT miter of the
old and new modules over 12 cycles with all inputs free.

**An inferred latch.** The crossbar's routing block declared `automatic int m`
inside an `if`. Vivado inferred a mux; Verilator and sv2v both saw a latch, since
the hoisted declaration is only assigned on the taken path.

**A function with an output argument.** `pick_next` used an `output` port, which
SystemVerilog allows and Verilog-2005 does not. Vivado and Verilator accept it;
Icarus rejects it, which blocked open-source simulation entirely. Rewritten to
return a packed `{found, index}`.

### The remaining critical path

With the DMA compare fixed, the next path surfaced and it is structural:

```
ex_mem_rd (flop)
  → forwarding compare vs id_ex_rs1/rs2
  → forwardA/B select (fanout ~65, both operand muxes)
  → operand mux → ALU → branch condition
  → ex_branch_taken (combinational)
  → id_ex_flush → the enable term on every ID/EX flop (fanout ~200)
```

One combinational path from a pipeline register, through forwarding, the full
ALU, branch resolution, and into the control of an entire pipeline stage. It is
the same path Vivado reported at +0.248 ns on the FPGA, where carry chains made
the ALU compare nearly free.

The corner spread tells the story: at 30 ns the typical corner has **+16.6 ns**
of slack and the fast corner **+21.3 ns**, while the slow corner has +2.50. The
design is not slow, it is corner-limited — it would close near 14 ns at `tt`
alone.

Shortening it means architectural change — removing `ex_branch_taken` from the
flush term and squashing differently, or resolving branches in a dedicated
comparator beside the ALU. Both alter pipeline control, and the ZedBoard was no
longer available to verify them on hardware, so they are deliberately left as
future work rather than shipped unverified.

### Known limitation

**45,418 max-slew violations remain at signoff**, all at the slow corner. Timing
is met and DRC/LVS are clean, but those transition times exceed the library's
recommended limit. OpenROAD's `repair_design` works from placement-estimated
parasitics and reported finding and fixing 644 violations; signoff STA, using
extracted post-route parasitics at the slow corner, measures tens of thousands.
The repair step and the checker are not looking at the same thing. This is a
characteristic of the flow rather than a misconfiguration, and it is stated here
rather than omitted.

## 3. Reproducing

```bash
# convert SystemVerilog for the open-source flow
sv2v -DSYNTHESIS --write=build/asic_sv2v/minerva.v -Irtl/common <rtl files>

# harden
librelane asic/config.json

# prove the netlist executes code
./scripts/gate_sim.sh
```

`scripts/gate_sim.sh` requires `-DFUNCTIONAL -DUNIT_DELAY=#1`. Without them the
Sky130 cell models elaborate into an all-X state in which the AXI handshakes
appear to complete and every readback is `xxxxxxxx` — indistinguishable from a
broken netlist, and not one.

## What P5 produced

- A fault-injection campaign of 1,312 runs, agreeing with an independent
  reference model on every classified injection
- Two bugs found in a design that had passed hardware bring-up
- An RV32I core with cache, crossbar and DMA hardened on Sky130, timing-clean at
  33 MHz across all corners, DRC/LVS/antenna clean
- A post-route netlist proven to execute real code
- Two RTL issues the FPGA flow could not have surfaced, one fixed with a formal
  equivalence proof
